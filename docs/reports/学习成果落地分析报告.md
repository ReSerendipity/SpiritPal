### 4.2 已应用技术亮点总结

#### A. 架构设计亮点

1. **Monorepo 物理隔离**（apps/desktop + apps/mobile + packages/shared）实现了桌面端和移动端的完全解耦，便于并行开发和独立部署。

2. **Rust 后端 + TypeScript 前端**结合了 Rust 的性能和安全优势与 TypeScript 的开发效率，优于纯 Python/C#方案。

3. **Zustand + persist**提供了简洁的状态管理和自动持久化，相比 Redux 更轻量。

4. **插件化能力扩展**（Tauri Plugin 生态）通过官方插件（sql/fs/notify/shortcut 等）实现了丰富的系统能力，无需手写 Rust 命令。

5. **8×9 spritesheet 标准化**对齐了 OC-Claw/OpenPets 的行业标准，便于宠物资源互换。

#### B. 核心算法亮点

1. **HP Tier × PetState 概率矩阵**（behaviorEngine）用饱食度分级 × 状态枚举决定动画选择，比 VPet 的纯随机选择更精细。

2. **梦境记忆巩固**（dreamingConsolidation）在 sleep 时进行记忆筛选和强化，参考 OpenMemory 的双过程理论，符合认知科学原理。

3. **实体图灵链接**（entityLinking + entityGraph）构建了结构化的知识图谱，支持更智能的回忆触发。

4. **角色偏好倍率**（getCharacterMultiplier）增加了游戏的深度，不同角色有独特的喜好和厌恶。

5. **离线衰减计算**（OFFLINE_HUNGER_DECAY_PER_HOUR）合理模拟真实在线时间，避免离线作弊。

#### C. 安全设计亮点

1. **Capability 权限控制**充分利用 Tauri v2 的 ACL 机制，前端 API 调用受严格限制。

2. **Path Traversal Guard**防止恶意路径穿越攻击，保护文件系统安全。

3. **PII 脱敏**在处理用户数据前自动遮蔽敏感信息，符合隐私法规要求。

4. **加密存储 + 密钥派生**使用机器 ID 派生密钥，确保数据无法被轻易窃取。

5. **SRI 完整性校验**防止资源被篡改，保障前端代码的完整性。

### 5.3 关键技术缺口原因分析

#### A. MCP Server 未实现（缺口原因：架构方向差异）

**根本原因**：SpiritPal 初始定位为"养成系桌宠"，agentTools 设计为"宠物→系统"单向驱动（宠物执行系统操作）。OpenPets 的"MCP 工具暴露给 AI 代理"是反向能力（代理→宠物）。

**影响**：缺少与 AI 编码助手的深度集成能力，无法实现"编码时宠物自动展示思考/编辑/测试状态"。

**解决路径**：新增独立的 MCP server（非替换现有 agentTools），实现 3 工具（spiritpal_status/spiritpal_react/spiritpal_say）。

#### B. 视觉感知未实现（缺口原因：优先级较低）

**根本原因**：视觉感知涉及截屏隐私问题，且需要额外调度和计费 LLM Vision API，初期优先级定得较低。

**影响**：AI 无法感知用户当前屏幕内容，只能被动响应用户描述。

**解决路径**：本地截屏 + 用户授权 + 可选开启 + 明确隐私提示。

#### C. 时间线索引未完成（缺口原因：功能分散）

**根本原因**：keyframeMemory 模块已建立，但时间线 UI（MemoryVisualization）和功能完善（按时间过滤检索）分散在不同迭代周期。

**影响**：用户无法直观查看记忆的时间分布，检索不能按时间范围过滤。

**解决路径**：补全 keyframeMemory 的时间过滤功能 + 开发时间线 UI 组件。

#### D. 代码插件缺失（缺口原因：技术复杂度高）

**根本原因**：代码插件需要沙箱隔离、权限控制、安全风险防护，实现复杂度远高于 JSON 配置。TypeScript 无法像 C# 那样动态加载程序集，需寻找替代方案（WebAssembly/JS sandbox）。

**影响**：MOD 作者只能修改配置，无法添加新逻辑，限制了生态创新能力。

**解决路径**：采用 QuickJS 或 Isolates 实现 JS 沙箱 + 严格的权限模型（参考 OpenPets SDK v3）。

    // Level 1: 精确匹配
    if (has(hpTier, state)) return select(hpTier, state)
    
    // Level 2: 向下兼容（更高 hpTier）
    if (hpTier < 3 && has(hpTier + 1, state)) return select(hpTier + 1, state)
    
    // Level 3: 向上兼容（更低 hpTier）
    if (hpTier > 0 && has(hpTier - 1, state)) return select(hpTier - 1, state)
    
    // Level 4: 任意非最低状态
    for (tier = 3; tier >= 1; tier--) {
      if (has(tier, state)) return select(tier, state)
    }
    
    // Level 5: 兜底 idle
    return getDefaultIdle()
  }
