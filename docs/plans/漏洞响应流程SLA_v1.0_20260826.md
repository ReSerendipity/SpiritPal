# SpiritPal 漏洞响应流程与 SLA

**版本**: v1.0  
**生效日期**: 2026-08-26  

---

## 1. 漏洞分级

| 级别 | 定义 | 示例 |
|------|------|------|
| **P0 (Critical)** | 远程代码执行 / 任意文件读写 / 密钥泄露 | IPC 命令注入、路径遍历导致系统文件读取 |
| **P1 (High)** | 敏感数据泄露 / 权限绕过 / 加密失效 | settingsStore 明文存储、SRI 校验缺失 |
| **P2 (Medium)** | 信息泄露（低敏感）/ 配置不当 | 调试日志泄露、CSP 过于宽松 |
| **P3 (Low)** | 最佳实践未遵循 / 文档缺失 | 缺少 SBOM、无 Dependabot |

## 2. 响应时限 (SLA)

| 级别 | 确认时限 | 修复时限 | 发布时限 |
|------|---------|---------|---------|
| P0 | 4 小时 | 24 小时 | 48 小时内发布热修复版本 |
| P1 | 1 个工作日 | 3 个工作日 | 下一个版本发布 |
| P2 | 3 个工作日 | 1 个版本周期 | 下一个版本发布 |
| P3 | 1 周 | 按计划排期 | 按计划排期 |

## 3. 响应流程

```
发现漏洞
  │
  ├─ 外部报告 → GitHub Security Advisory (私密披露)
  │               │
  │               ▼
  ├─ 内部发现 → 创建 Issue (标记 security)
  │               │
  │               ▼
  └───────────────┤
                  ▼
          ① 确认漏洞 (SLA: 按 P0-P3)
                  │
                  ▼
          ② 分级与分配责任人
                  │
                  ▼
          ③ 开发修复分支 (security/fix-xxx)
                  │
                  ▼
          ④ 代码审查 (至少 1 人)
                  │
                  ▼
          ⑤ 测试验证 (单元测试 + 安全回归)
                  │
                  ▼
          ⑥ 发布修复版本
                  │
                  ▼
          ⑦ 审计日志记录 (audit_log: security_event)
                  │
                  ▼
          ⑧ 公开披露 (P0/P1 发布后 7 天)
```

## 4. 依赖漏洞响应

CI 流水线中的三层依赖扫描（pnpm audit / cargo audit / osv-scanner）发现漏洞时：

| 漏洞级别 | CI 行为 | 响应时限 |
|---------|--------|---------|
| CRITICAL | CI 阻断 (exit-code: 1) | 24 小时内修复或升级 |
| HIGH | CI 阻断 (pnpm audit --audit-level=high) | 3 个工作日内修复 |
| MEDIUM | CI 不阻断（仅报告） | 1 个版本周期内评估 |
| LOW | CI 不阻断 | 按计划排期 |

## 5. 密钥泄露响应

如发现密钥（API Key / 签名密钥 / 机器 ID 派生密钥）泄露：

1. **立即**（15 分钟内）：撤销泄露的密钥
2. **1 小时内**：生成新密钥并更新所有使用位置
3. **4 小时内**：审计日志记录泄露事件 + 评估影响范围
4. **24 小时内**：通知受影响用户（如涉及用户数据）

## 6. 联系方式

- **私密漏洞披露**：GitHub Security Advisory
- **安全相关 Issue**：标记 `security` label
- **紧急联系**：通过项目仓库 Issues 联系

## 7. 审计与回顾

- 每季度回顾漏洞响应 SLA 达成率
- P0/P1 漏洞修复后进行事后分析（Post-mortem）
- 安全评估报告每年至少更新一次
