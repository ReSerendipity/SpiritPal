## 二、机制一：依赖生态自动跟踪（每周）

**组成**：`scripts/track-deps-ecosystem.mjs`（纯内置 fetch，无新依赖）+ `.github/workflows/deps-watch.yml`（每周一 04:23 UTC + 手动 workflow_dispatch）。

**判读**（脚本退出码语义）：
| 退出码 | 含义 | workflow 行为 |
|---|---|---|
| 0 | 无可行动变化 | workflow 绿，无动作 |
| 1 | 发现可行动变化（官方支持 pixi 8 / tauri-gtk 修复链可用） | workflow 仍绿；自动创建 `[deps-watch]` 跟踪 issue（幂等，已有未处理 issue 则跳过） |
| 2 | 上游查询失败（网络/限流） | 静默，下周自动重试（避免抖动刷 issue） |

**绿主页策略**：deps-watch 永远不会因「发现变化」变红——变化以 issue 承载，主页 Actions 保持全绿；issue 即人工评估的触发器。

**维护**：
- 新增需跟踪的 fork：在脚本 `PIXI_ECOSYSTEM` 数组登记（role=fork 仅信息；判定升级只认 official）。
- glib 修复线常量（`GLIB_FIXED_MINOR`/`GTK_FIXED_MINOR`）随 RUSTSEC 修复版本变化时更新。
- schedule 连续 60 天无仓库活动会被 GitHub 自动禁用——仓库活跃即无碍；停用后重启：Actions 页手动 Enable。

## 三、机制二：安全漏洞扫描与响应

**已有扫描面（不重复建设）**：ci.yml `dependency-vuln-scan` job —— push/PR + **每周一 03:00 UTC schedule** 触发，含 pnpm audit（JSON 落盘）+ cargo audit（JSON 落盘）+ `security_gate.py` 棘轮基线（CRITICAL/HIGH 超基线即 CI 红）+ osv-scanner（报告 artifact，14 天留存）。Secret 扫描由 trivy FS job 承担。

**已知豁免基线**（动基线必须留痕，更新 security_gate 棘轮 + 本表同步）：
| 漏洞 | 豁免原因 | 出路 |
|---|---|---|
| glib RUSTSEC-2024-0429（medium） | tauri 2.x 锁 gtk-rs 0.18，上游无修复链（§一 2.2） | tauri 3.x / gtk-rs 0.20 可用后升级关闭 |

**响应 SOP（新漏洞出现时，按严重级分流）**：
1. **CRITICAL/HIGH**（CI 因棘轮超标变红 = 唯一允许的"红"信号，48 小时内处置）：
   a. 读 CI 的 pnpm-audit.json / cargo-audit.json 定位包与利用面；
   b. 三选一（按可逆性 > 改动面最小排序）：`overrides`/`cargo update --precise` 锁修复版（优先）→ 升级直接依赖（major 需专项评估 + 回滚点 tag）→ 无法修复且有缓解时 `security_gate.py` 基线接受并在本表登记理由；
   c. 全量门禁复跑（lint / vitest / cargo test / clippy）后提交，commit 写明漏洞编号。
2. **MEDIUM/LOW**：登记到本表（或确认已被棘轮覆盖），随下次发版评估；不影响发版门禁。
3. **上游阻塞型**（如 glib）：维持受阻记录 + deps-watch 自动盯上游，修复链可用再动。

## 四、机制三：发版前一键预检（v0.1.x 起强制）

```bash
node scripts/pre-release-check.mjs                    # 标准预检
node scripts/pre-release-check.mjs --local-artifacts  # 附加本地产物+签名检查
node scripts/pre-release-check.mjs --skip-remote      # 本机 GitHub 加速器 MITM 环境下跳过远程项并留痕
```

检查项：版本三处一致（sync-version --check）→ 工作区干净且在 main → 包门禁 <30MB → updates.json 可达（发布后版本比对由 release.yml `publish-updates` 回读负责）→（可选）本地 setup.exe+.sig。

与 CI 门禁分工：本地预检防「带病打 tag」（省 CI 重试）；CI 侧 verify-release-version.yml + release.yml Package Size Gate 是最终门禁，两者内容一致、口径相同。

## 五、机制四：docs/execution 治理防护与应急预案

**门禁**：structure-guard 新增 `Execution docs tracked guard`（`scripts/check-exec-docs-tracked.mjs`）：核心执行文档（RELEASE_VERIFICATION + 执行对照表 + 落地总结，新增执行文档后登记 `EXEC_DOCS_REQUIRED`）必须被 git 跟踪。再次被移出跟踪 → CI 显式红（这是防"静默丢失"的信号红，与绿主页策略的例外关系见 §七）。

**self-purify 再犯应急预案**（历史：e2a9699 移出 → 用户授权恢复 3578975）：
1. **不对抗**：不在 CI 层与家族机制反复互相 revert；
2. 本地磁盘 `docs/execution/` 永远有一份完整副本，工作不依赖入库状态；
3. 凭用户 2026-09-11 明确授权（commit 3578975 message）恢复入库；若家族机制再判定违规，升级到家族治理层（ReSerendipity/.github）裁决「执行文档是否应入库」的口径，或按裁决迁移目录；
4. 裁决期间门禁红属预期，处理完毕即恢复绿。
