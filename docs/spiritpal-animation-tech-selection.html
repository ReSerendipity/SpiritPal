二、逐方案分析

1. 精灵图 Sprite Sheet 默认 MVP 首选

  • 适用：像素风、Q 版多角色、低配机器、安装包/内存敏感。
  • 优势：生态最成熟（OpenPets 宠物包 = 精灵图 + 动画映射 + 元数据）；加载即播放、无解码开销；体积性能最优。
  • 代价：逐帧资产成本高——动作数量 × 帧数线性膨胀；放大模糊；多角色需维护多套精灵表。
  • 落地：沿用 desktop-pet 生态的 8×9 精灵表行映射约定；AI 生图 → 绿幕抠图 → 拼精灵表的自动化管线已被社区验证。

2. WebM 透明视频 手绘动画量大时最优

  • 适用：手绘流畅动画、动作数量大（几十上百个动作）。
  • 优势：dsh-pet 以 91 个动作证明可行；手绘逐帧动画转视频后资产成本远低于精灵图；衔接顺滑。
  • 风险：Windows 透明通道不保证，需色度键（绿幕/紫幕）抠像兜底；首帧解码有内存尖峰；循环需掐帧。
  • 落地：素材统一绿幕录制 → 运行时抠像；动作切换前预加载下一段视频。

3. Live2D 二次元体验上限最高

  • 适用：二次元立绘角色，要求呼吸、眨眼、表情、口型。
  • 优势：市面 AI 桌宠的主流答案；实时网格形变，一套模型驱动全部表情，无需逐帧资产。
  • 代价：模型制作门槛高（.model3.json 需 Cubism 编辑器，成本大）；SDK 有授权条款。
  • 落地：角色若是现成 Live2D 模型（或团队能产），这是 2D 方案中表现力上限最高的选择。

4. Lottie 体积敏感 / 轻量吉祥物

  • 适用：体积敏感、需要矢量无限缩放的简洁吉祥物 / UI 角色。
  • 优势：JSON 驱动、单文件几 KB~几十 KB；矢量任意缩放清晰；程序可控性强（进度、颜色、播放状态）；ai-bubu（Tauri + Vue 3）已验证。
  • 局限：复杂角色、骨骼形变、细腻表情表达弱——适合「轻量吉祥物」而非「高表现力角色」。

5. Spine 2D 骨骼 游戏动作型 2D

  • 适用：2D 角色要骨骼形变、网格动画，又不想上 3D。
  • 优势：游戏行业 2D 骨骼动画标准；运行时小；骨骼/网格形变比 Live2D 更自由，动作库可复用换皮；DyberPet 已将其列为计划中的升级方向。
  • 代价：Spine 编辑器（Pro）授权费用；需要会摆骨骼、K 动画的美术。
  • 与 Live2D 的区别：Spine 偏「游戏角色动画」（跑跳攻击），Live2D 偏「立绘形变表现」（呼吸眨眼口型）。

6. VRM / 3D 远期 / VTuber 联动

  • 适用：3D 角色、VTuber 联动、多视角展示。
  • 优势：Super Agent Party（Electron + Python/FastAPI，支持 VRM 桌宠自定义、3D/2D 虚拟角色）已验证完整路线；模型资产丰富（VRoid Hub 等）；可接 VTube Studio 联动直播。
  • 代价：3D 渲染开销（GPU、内存）；模型面数/穿模/捏脸调优成本；桌面常驻场景资源占用显著高于 2D 方案。
  • 落地：three.js / PixiJS + VRM Loader。

7. PSD 自动建模 Anime2.5DRig 无美术产能的兜底

  • 适用：没有美术产能、只有分图层 PSD 的团队/个人。
  • 优势：852wa/Anime2.5DRig 将分图层 PSD 拖入浏览器即自动 rigging 生成 2.5D 动画，门槛最低；dsh-anime25d-pets 插件已接入 DSH 桌宠（原 Live2D 方案模型制作门槛高，本方案只需一张分图层 PSD）。
  • 代价：动画质量受自动 rigging 限制，复杂动作需手动调；图层命名/拆分规范决定成品质量。

四、决策检查清单

1. 有没有美术/动画产能？没有 → PSD 自动建模（Anime2.5DRig）或精灵图生态现成素材

2. 角色是像素风/简洁吉祥物？是 → 精灵图；体积敏感且要矢量缩放 → Lottie

3. 二次元立绘、要呼吸/眨眼/表情？是 → Live2D

4. 手绘动画素材量大（几十个动作）？是 → WebM（配绿幕抠像兜底）

5. 要骨骼形变但不上 3D？是 → Spine

6. 要 3D / VTuber 联动？是 → VRM（SuperAgentParty 路线，可接 VTube Studio）
